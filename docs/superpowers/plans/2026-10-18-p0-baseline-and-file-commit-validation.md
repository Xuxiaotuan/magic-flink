## 1. 范围与验收边界

### 全局约束

- 用户只写 YAML，不上传 JAR、代码、脚本或运行时插件；所有新增能力随平台制品发布。
- 自研服务；SeaTunnel、Flink CDC 仅供参考，不加入 P0 运行依赖。
- 一个工程，按 spec、control、runtime、connectors、app 划分职责，不先拆多个构建模块。
- Flink 核心和 Planner 归固定镜像；应用和适配器归一个 shaded JAR。镜像内固定的 Flink 文件系统插件仍需统一扫描，不能由用户替换。
- 有界 BATCH，输入及候选落 Parquet；下游只读元数据接纳的 SEALED Manifest。
- 只接受真实提交证据、成功终态和完整内容核验的联合证明；不得把目录扫描、日志成功字样或单独 FINISHED 当成封存依据。
- P0 只做两份 PostgreSQL JDBC 固定输入、一个 PostgreSQL 目标和一种内部存储的最小验证。三类新增 Source 的实现与实测在 P4。
- 本计划不授权部署或故障注入到生产；实验只能使用已确认的隔离测试范围、合成数据和专属对象前缀。
- 后续执行计划不自动包含提交、推送或发布；这些操作按届时明确授权执行。本轮不创建代码、POM、镜像、CR 或测试脚本。

### 重点复核的五种失败输入

1. 失败 task attempt 的文件看似完整，却被混入最终清单：T03、T07-F03。
2. 文件已提交但提交索引未保存，恢复程序误判成功：T07-F04。
3. 空批次、空 writer 或过滤后空结果，被当作缺失或提前完成：T06、T07-F10。
4. 旧尝试在取消/替换后上报成功，错误触发封存或下游：T04、T07-F09。
5. 存储返回超时或证据重复到达，恢复时改写同一标识的内容：T06、T07-F05/F11。

### 2.2 依赖归属

| 归属 | 内容 | P0 必须排除的错误 |
|---|---|---|
| 固定运行镜像 | Flink 1.20.5 核心/Planner、JDK、唯一 S3 插件及其隔离依赖 | 应用 JAR 重复装载 Flink 核心；两个 Planner；两个 S3 scheme 实现 |
| 应用 fat JAR | 自研入口/验证逻辑、pgJDBC、所需文件/格式适配依赖 | 镜像已有类与应用重复；SPI 丢失；同时引入多套日志绑定 |
| 构建与测试环境 | Maven、Shade/测试插件、实验工具 | 测试依赖或故障开关意外进入生产入口；只扫描应用不扫描镜像 |

以实际镜像清单和依赖树决定文件/格式适配依赖是否打包，保证每个运行类只有一个明确来源。不能只因“属于 Flink”就全部设为 provided，也不能把 Parquet 标记 provided 的 Hadoop 依赖想当然地当作运行时已存在。已核对 [Parquet 模块 POM](https://github.com/apache/flink/blob/release-1.20.5/flink-formats/flink-parquet/pom.xml)；T02/T05 要验证最终 classpath。

S3 插件内部的 Hadoop/AWS SDK 按插件制品锁定和扫描，不单独覆盖其版本。Service 如需直接 SDK 才能实现元数据对象的原子 create-if-absent，T03 必须先证明必要性，T02 再登记精确 SDK 坐标、版本、隔离位置和扫描结果；在此之前不能把“Flink 文件系统可写文件”当成“元数据不可变写入已实现”。插件安装方式见 [Flink S3 文档](https://nightlies.apache.org/flink/flink-docs-release-1.20/docs/deployment/filesystems/s3/)。

### 2.3 从候选到冻结

T02 形成候选锁定表；T08 才形成通过验收的 ReleaseManifest。表内必须包含每个直接/传递依赖的精确版本、制品来源和摘要，JDK 完整 build、目标平台架构、基础及最终镜像 digest、Operator Chart/CRD/镜像摘要、存储服务端版本、测试配置摘要和扫描报告引用。

Kubernetes、存储产品、镜像 digest、Parquet/Hadoop/SDK 传递版本不是可以留到 P1 再补的空项。它们分别由 T01、T02 的负责人获取；任一项未取得，T08 不允许标记“版本已冻结”。本文不伪造尚未解析或获取的版本和 digest。

候选因扫描或准入被否决时，每次只调整一个明确原因涉及的依赖组合，重做受影响验证；改变 Flink/Sink/S3 实现则全部重做 T03、T05–T07。P0 不同时维护两套主版本路线。

- [ ] 登记 `orders_jdbc`、`customers_jdbc` 两份固定批次：100 笔订单的 order_id 为 1…100、金额为 1.00…100.00，10 个唯一客户，固定客户映射且全部匹配。预期结果 100 行、总额 5050.00。另建独立空批次与空输出场景。
- [ ] 说明批次完成后如何禁止修改、控制数由谁提供、版本保留多久。上游控制数来自固定 fixture 账本，不从采集计数器反推。

**验收：** 环境与数据身份可明确复述；有实际访问和版本取证路径；任何产品/权限未知有责任方和获取动作。只有本机临时对象存储时，允许做预实验，但目标获准存储的验收仍未完成。

- [ ] 核对 Flink、Operator、JDK 与实际 Kubernetes 的兼容信息；明确 Operator 自身 JVM 与作业 JVM 是两个运行边界。
- [ ] 先做发行包及依赖扫描；若触发行内阻断策略，记录具体条目及处置结论后再继续，不自行忽略。

### T03：评估合法文件集合的获取路径

**负责人角色：** Flink/存储研发。**输入：** T02 的精确 Flink 和 S3 插件。**输出：** file-commit-protocol.md 中的接口路径、字段来源表与技术可行性结论。

- [ ] 阅读固定 tag 的 FileSink、FileWriter、FileSinkCommittable、FileCommitter、对应 PendingFileRecoverable 和 S3 RecoverableWriter；记录源码 commit 和方法定位。
- [ ] 逐项确认能否获得实际最终对象键、task attempt 身份、已接受的提交结果、writer 结束标记，以及输入逻辑分片完成信息。标记每个字段来自原生运行时、适配器还是固定计划。
- [ ] 首选薄封装：复用原生文件提交，捕获可证明已成功的提交结果，再生成 CommitEvidence。可以隔离固定版本的 Internal API 依赖，但必须列清升级成本；不使用反射猜私有字段、日志解析或目录枚举兜底。
- [ ] 说明聚合终结条件：预期 writer 集合及其结束证据齐全、每份预期提交有成功证明、无未判定请求，并与最终被接受的 task attempt 对齐。writer 无输出也必须完成；输入分片数不能替代 writer 数。
- [ ] 区分“有一个提交成功”与“完整集合已经成功”；不能在遍历一批提交请求的中途就发布全局索引。说明同文件重复提交如何归一，以及错误内容重复如何拒绝。
- [ ] 明确证据聚合位置、持久化时点及失败处理；记录能否在不 fork Flink 的情况下完成最小原型。若仅能取得待提交对象而拿不到成功/胜出语义，结论为 NO_GO，返回提交方案评审。

**已查明的源码事实：** 1.20.5 的 FileSinkCommittable 和 FileCommitter 标记为 Internal；committable 还包含清理类消息。FileCommitter 对 pending 文件调用恢复后的提交方法，不能将每条 committable 都计为成功数据文件。[FileSinkCommittable](https://github.com/apache/flink/blob/release-1.20.5/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/FileSinkCommittable.java)、[FileCommitter](https://github.com/apache/flink/blob/release-1.20.5/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/committer/FileCommitter.java)。

**验收：** 字段来源和终结条件能对应具体接口，形成可在 T05/T06 验证的薄封装方案，结论为 GO_TO_SPIKE 或 NO_GO。前者只允许进入原型实验，不证明实际可产出完整集合；后者应返回设计评审。若需要修改 Flink 本体或另起通用事务日志，也暂停并返回评审，不把它作为普通实现细节追加。

### T04：冻结对象与恢复判定合同

**负责人角色：** 服务研发。**输入：** T01 fixtures、T03 证据获取结论。**输出：** platform-contracts.md、file-commit-protocol.md 的规范部分及判定表。

- [ ] 定义 ConnectionProfile、两个 DatasetDefinition、OutputDatasetDefinition 与 RuntimeProfile 的字段、版本和权限；同一物理连接别名必须共享额度。
- [ ] 固定 StagePlan、CommitEvidence、Manifest、StageReceipt 字段来源及摘要规范；参数值、逻辑阶段键、外部身份与当前尝试不可省略，见第 5 节。
- [ ] 为对象写入定义 create-if-absent：同键同内容幂等，同键异内容冲突；GET 超时不能当不存在。对照实际存储能力选择受验证的原子机制，不能仅用“先 HEAD 后 PUT”。
- [ ] 将当前尝试资格、取消标记、phase 和数据版本核对，与 SEALED 引用/阶段完成放进同一元数据库事务；明确只有事务接纳的清单可被后续读取。
- [ ] 冻结首次发布合同：查询成功缺行才解释为 revision=0；指针唯一键初始化、CAS 和历史同目标事务；原 publicationId 并发重送复查历史；取消与授权点在元数据库串行化。P0 做局部数据库协议实验，不冒充 P2 的完整目标发布验收。
- [ ] 固定第 6 节资源档位、重试预算及证据等待期限，并在小数据验证中确认不会无限等待或无限重试。

**验收：** 每个故障窗口只有明确的补证据、废弃重跑、等待 UNKNOWN 或拒绝分支；取消先提交不能授权发布，授权先提交只能返回取消过晚。局部事务实验的正反例和预期已明确，运行验证交给 T07；完整 API 和跨进程竞争回归仍归 P1–P3。

### T05：建立单一制品的最小真实贯通

**负责人角色：** 平台研发。**输入：** T02 锁定表、T03 接口结论。**输出：** 单个实验应用 JAR、固定镜像、PackagingSmokeIT 结果。

- [ ] RunnerMain 经 Operator Application 运行最小有界图，产生实际 Parquet 文件与提交证据；Service/Runner 使用同一 JAR 摘要。
- [ ] 验证 RowData/Schema、DECIMAL 和日期时间在文件中保真；检查 JDBC、Parquet Factory 和 S3 FileSystem 的 SPI/类加载。
- [ ] 检查应用包、最终镜像、实验工具及全部运行依赖的扫描结果；故障注入仅能通过受控测试角色启用，生产角色拒绝这些参数。

**验收：** 两入口都完成实际工作，Operator 观察到相应作业身份与终态，JAR 和镜像摘要一致。保存构建日志、依赖树、重复类/SPI 检查、扫描报告和执行证据。此结果不代表完整 BatchService 已开发。

### T06：验证正常链路及对象存储语义

**负责人角色：** Flink/存储研发。**输入：** T04 合同、T05 制品。**输出：** 无故障和存储能力实验记录。

- [ ] 在真实目标测试存储上完成：固定输入 → BATCH FileSink → CommitEvidence → Manifest → 元数据 SEALED → 只按清单回读。
- [ ] 分别运行并行度 1 和 4；额外生成多文件数据，保证确有多个成功文件而不只是扩大并行度。结果与独立 fixture 的行多重集合精确相等，不仅比较总行数。
- [ ] 验证合法零行输入、部分 writer 零行、SQL 过滤后全空、非法空批次；原生 Sink 若生成零行 Parquet，需记录这种表示，不能把文件数误等同记录数。若需规范化为零文件清单，必须在完整证据下验证并排除零行文件。
- [ ] 验证实际存储的 multipart 完成/恢复、HEAD/GET 可见性、原子 create-if-absent、重复写内容冲突、TLS 和权限失败。ETag 不作为 SHA-256 替代。
- [ ] 对候选显式文件逐个读回核验 Schema、大小、行数和 SHA-256；在同一前缀放置未列入清单的垃圾文件，确认消费方不会扫描并读取它。
- [ ] 记录峰值连接、缓冲内存、字节量、耗时及对象数，为有限资源档位提供事实；不要求在此阶段证明生产吞吐。

**验收：** 正常路径内容精确、空输出明确、存储语义与设计吻合。任何关键存储能力不支持时 NO_GO；不能通过换成本地目录得到 PASS 后宣称目标对象存储可用。

## 5. 文件提交协议实验合同

### 5.1 最小对象与来源

| 对象 | 实验必须冻结的内容 | 允许来源 |
|---|---|---|
| StagePlan | runId、逻辑阶段键、stageAttemptId、固定输入版本、Schema、并行度、输出前缀、releaseId、计划摘要 | 先持久化的计划；不是运行后拼装 |
| CommitEvidence | 计划/资源身份、合法文件集合、提交身份、最终 writer 集合与结束标记、全部逻辑输入分片完成证明 | T03 确认的真实提交与运行终结信息 |
| Manifest | 固定 manifestId、证据摘要、排序后的显式文件列表、Schema、SHA-256/字节/行数、固定源版本 | 完整提交证据及实际文件回读 |
| TerminalObservation | CR UID、generation、Flink Job ID、成功终态及持久观察记录 | 受控 Operator/Flink 查询；Pod Running 不是终态 |
| StageReceipt | 对已确认阶段事实的引用及确定结果 | 上述事实和元数据库记录，可重建，不作为循环自证 |

规范化摘要采用 UTF-8 JSON，键排序、文件列表按规范对象键排序；禁止浮点编码金额，时间采用固定 UTC 表示。不可变内容中的时间取原始计划/提交证据，恢复进程的当前时间单独记审计字段。每个规范版本固定算法，禁止同一标识在不同恢复轮次产生不同语义摘要。

### 5.2 首轮实验的收敛配置

- 显式 BATCH，不用 streaming checkpoint 完成回调替代批结束协议。
- 固定并行度，关闭推测执行及自动并行度变化；不启用 compaction、自动 schema 演进或动态分桶。解除这些限制需新增相应验收。
- 每次平台尝试使用独立前缀；批内多文件滚动可用，但不能依赖墙钟分桶决定 manifest 身份。
- 提交证据只有在 T03 定义的完整集合成立后才写最终索引；局部记录、预提交消息和半份索引都不能 SEALED。
- JobManager 失败后是否能保留进度，由选定版本和配置实测；无法证明旧产物完整时，确认旧执行终止后从原固定输入用新尝试重跑。不要求 P0 实现所有批作业断点恢复。
- 成功终态丢失且无法恢复时不以完整文件反推成功；保持 UNKNOWN，只有明确确认停止后才能废弃重跑。

FileSink 的批模式与流模式文件可见性不同，官方说明见 [FileSystem/FileSink](https://nightlies.apache.org/flink/flink-docs-release-1.20/docs/connectors/datastream/filesystem/)。这些说明支持选型研究，不能替代本项目 CommitEvidence 的实验。

### 5.3 必须证明的六个不变量

1. 每个进入 Manifest 的文件属于一个明确、合法、当前尝试的提交集合。
2. 完整性由预期集合与终结证据共同决定，不由“已收到多少条成功消息”猜测。
3. Manifest 已写但未被元数据库接纳时，下游不可见。
4. SEALED 引用与阶段完成同事务更新；同 ID 不允许不同内容。
5. 证据完整时只补建清单/回执，不重新执行数据图；证据不完整时不抢救拼接文件。
6. 旧尝试、取消后的证据可以归档，但不能影响当前尝试、下游意图或发布授权。

## 6. P0 实验资源与时间基线

以下为小数据实验的建议初值，不是生产容量承诺。T01 确认可承载后，T04 将确定值固定到实验配置；不足时先调整并记录，不在一次验收中漂移。

| 参数 | 初值 | 约束 |
|---|---|---|
| 活跃运行 / Flink Applications | 2 / 2 | 全局共享；每运行采集上限仍为 2 |
| Flink 并行度 | 正常为 1，对照为 4 | 4 个可用 slot；按实测 JVM 内存配置 JM/TM，不据此宣称性能合格 |
| 同物理 PostgreSQL 的连接总预算 | 8，其中探测最多 2 | 采集/检查/写入共享；不让多个别名各占 8 |
| Service 检查池 / 文件核验池 | 2 线程 / 2 线程 | 分开限额；核验单任务缓冲上限 16 MiB，流式读取 |
| INLINE 检查上限 | 10,000 行且 8 MiB，30 秒 | 上限是总读取规模，非每页；超限 ERROR，不能返回部分 PASS |
| 证据等待 | 成功终态确认后最多 120 秒 | 轮询 5 秒；不可达是 UNKNOWN，不等同确实缺失 |
| 单阶段 / 单实验 | 15 分钟 / 30 分钟 | 超时停止新尝试，但继续追踪已发生副作用 |
| 自动阶段重试 | 最多 1 次 | 缺提交证据的废弃重跑和 INLINE 转 FLINK 都消耗预算 |
| 输入/证据保留 | 本次实验结束后至少 7 天 | 仍被活动实验引用时不回收；行内策略更长则从其规定 |

其他未来连接类型的请求限速在 P4 确定；P0 不用未经测量的 HTTP/BQ 预算冒充四源资源配置。首次准备数据和测试保留期不得涉及真实客户数据。

## 7. 故障验证矩阵

实验中的“小型元数据判定器”只验证事务和合同，不是完整 BatchService。T07 对下面每行记录 `NOT_RUN/PASS/FAIL/BLOCKED`，BLOCKED 必须列外部条件，不计为通过。

| 编号 | 对应设计用例 | 注入位置或操作 | 必须观察到的结果 |
|---|---|---|---|
| F01 | A12 基线 | 无故障，分别并行度 1/4，强制形成多个文件 | 合法文件集合完整，回读与独立 fixture 精确一致；不要求两次文件布局相同 |
| F02 | A12 | 文件未提交前终止 TaskManager；允许配置内重启 | 成功集合只含最终合法产物；无法恢复则确认停止后新尝试重跑，未提交文件不被接纳 |
| F03 | A12 | task attempt 失败/重试，同时延迟旧尝试完成信息 | 不把两个 attempt 的文件无条件合并；旧 attempt 不能靠先到消息获胜 |
| F04 | A27 | 实际文件提交完成后、完整 CommitEvidence 落盘前中断 | 超出证据等待且确认停止后废弃，使用新前缀重跑；目录中存在成品也不封存 |
| F05 | A26 | 完整证据和成功终态已持久化，Manifest 写前或写成功响应丢失 | 恢复得到同一个 manifestId/内容；不再采集/计算，不覆盖异内容 |
| F06 | A26 | Manifest 已持久化，SEALED 元数据事务提交前中断 | 恢复校验当前资格后补事务；未提交前下游不可读 |
| F07 | A26 延伸，A28 局部 | SEALED/阶段成功事务已提交、receipt 尚未生成 | 从持久事实补 receipt，数据图不重跑；完整协调器行为仍在 P1 验收 |
| F08 | A12/A27 | JobManager 失败，分别保留/丢失可恢复成功观察 | 可证明时恢复；不可证明时 UNKNOWN 或停止后废弃重跑，不能只凭文件或 CR 名称认领 |
| F09 | A24/A25 局部 | 在元数据中先取消或切换当前尝试，再投递旧证据 | 接纳事务拒绝，旧证据只归档；同时完成的两个有效输入互不误拒绝 |
| F10 | A33 | 合法空输入、部分 writer 空、全过滤为空、缺失一个结束标记 | 前三者有完整结束证明才可封存；缺标记不能以零文件或零行判成功 |
| F11 | A17 局部 | 篡改文件、复用 ID 写不同清单、GET 超时、并发 create-if-absent | 摘要错或冲突拒绝；超时 UNKNOWN；同 ID 同内容幂等，不发生覆盖 |
| F12 | A22/A23/A29 局部 | 目标指针缺行，两个首次发布竞争；授权/取消两种先后顺序 | 同 expectedRevision=0 至多一个提交；指针与历史同事务；取消胜出不授权，授权胜出取消过晚 |
| F13 | 资源基线局部 | 用小型元数据判定器争抢共享额度，重复预留及模拟失联 | 不重复扣还、不部分持有后等待；UNKNOWN 不释放；此实验不替代 P3 全集群配额验收 |

F01/F10 另做非法空批次负例；F04 另测源版本过期，必须失败而不是读取最新源。F05/F06 另测从错误 runId/计划摘要恢复，必须拒绝。F12 的数据库实验需覆盖同 publicationId 并发重复请求及目标事务回滚，不能仅测试不同 ID 的竞争。

### 每份实验记录的最小证据

executionId、时间、操作者、测试制品/镜像 digest、配置摘要、固定输入版本、实际资源 UID/Job ID、注入位置及命中证明、故障前后记录、预期与实测、最终对象/元数据摘要、判定及证据引用。

## 8. 进入 P1 的明确门槛

以下条件全部成立才为 **P0 GO**，不按通过率折算。

| 门槛 | 必需证据 | 否决条件 |
|---|---|---|
| G1 版本冻结 | T02/T08 精确依赖、环境、JAR 和镜像摘要、扫描报告 | 存在未解析版本、未准入依赖或证据来自不同发行组合 |
