## 1. 范围与验收边界

### 全局约束

- 用户只写 YAML，不上传 JAR、代码、脚本或运行时插件；所有新增能力随平台制品发布。
- 自研服务；SeaTunnel、Flink CDC 仅供参考，不加入 P0 运行依赖。
- 一个工程，按 spec、control、runtime、connectors、app 划分职责，不先拆多个构建模块。
- Flink 核心和 Planner 归固定镜像；应用和适配器归一个 shaded JAR。镜像内固定的 Flink 文件系统插件仍需统一扫描，不能由用户替换。
- 有界 BATCH，输入及候选落 Parquet；下游只读元数据接纳的 SEALED Manifest。
- 只接受真实提交证据、成功终态和完整内容核验的联合证明；不得把目录扫描、日志成功字样或单独 FINISHED 当成封存依据。
- P0 只做两份 PostgreSQL JDBC 固定输入、一个 PostgreSQL 目标和一种内部存储的最小验证。三类新增 Source 的实现与实测在 P4。
- 本计划不授权部署或故障注入到生产；实验只能使用已确认的隔离测试范围、合成数据和专属对象前缀。
- 后续执行计划不自动包含提交、推送或发布；这些操作按届时明确授权执行。本轮允许核心代码、POM 和本地单元测试；不创建镜像、CR 或执行安装/部署。

### 重点复核的五种失败输入

1. 失败 task attempt 的文件看似完整，却被混入最终清单：T03、T07-F03。
2. 文件已提交但提交索引未保存，恢复程序误判成功：T07-F04。
3. 空批次、空 writer 或过滤后空结果，被当作缺失或提前完成：T06、T07-F10。
4. 旧尝试在取消/替换后上报成功，错误触发封存或下游：T04、T07-F09。
5. 存储返回超时或证据重复到达，恢复时改写同一标识的内容：T06、T07-F05/F11。

### 2.2 依赖归属

| 归属 | 内容 | P0 必须排除的错误 |
|---|---|---|
| 固定运行镜像 | Flink 1.20.5 核心/Planner、JDK、唯一 S3 插件及其隔离依赖 | 应用 JAR 重复装载 Flink 核心；两个 Planner；两个 S3 scheme 实现 |
| 应用 fat JAR | 自研入口/验证逻辑、pgJDBC、所需文件/格式适配依赖 | 镜像已有类与应用重复；SPI 丢失；同时引入多套日志绑定 |
| 构建与测试环境 | Maven、Shade/测试插件、实验工具 | 测试依赖或故障开关意外进入生产入口；只扫描应用不扫描镜像 |

以实际镜像清单和依赖树决定文件/格式适配依赖是否打包，保证每个运行类只有一个明确来源。不能只因“属于 Flink”就全部设为 provided，也不能把 Parquet 标记 provided 的 Hadoop 依赖想当然地当作运行时已存在。已核对 [Parquet 模块 POM](https://github.com/apache/flink/blob/release-1.20.5/flink-formats/flink-parquet/pom.xml)；T02/T05 要验证最终 classpath。

S3 插件内部的 Hadoop/AWS SDK 按插件制品锁定和扫描，不单独覆盖其版本。Service 如需直接 SDK 才能实现元数据对象的原子 create-if-absent，T03 必须先证明必要性，T02 再登记精确 SDK 坐标、版本、隔离位置和扫描结果；在此之前不能把“Flink 文件系统可写文件”当成“元数据不可变写入已实现”。插件安装方式见 [Flink S3 文档](https://nightlies.apache.org/flink/flink-docs-release-1.20/docs/deployment/filesystems/s3/)。

### 2.3 从候选到冻结

T02 形成候选锁定表；T08 才形成通过验收的 ReleaseManifest。表内必须包含每个直接/传递依赖的精确版本、制品来源和摘要，JDK 完整 build、目标平台架构、基础及最终镜像 digest、Operator Chart/CRD/镜像摘要、存储服务端版本、测试配置摘要和扫描报告引用。

Kubernetes、存储产品、镜像 digest、Parquet/Hadoop/SDK 传递版本不是可以留到 P1 再补的空项。它们分别由 T01、T02 的负责人获取；任一项未取得，T08 不允许标记“版本已冻结”。本文不伪造尚未解析或获取的版本和 digest。

候选因扫描或准入被否决时，每次只调整一个明确原因涉及的依赖组合，重做受影响验证；改变 Flink/Sink/S3 实现则全部重做 T03、T05–T07。P0 不同时维护两套主版本路线。

## 5. 文件提交协议实验合同

### 5.1 最小对象与来源

| 对象 | 实验必须冻结的内容 | 允许来源 |
|---|---|---|
| StagePlan | runId、逻辑阶段键、stageAttemptId、固定输入版本、Schema、并行度、输出前缀、releaseId、计划摘要 | 先持久化的计划；不是运行后拼装 |
| CommitEvidence | 计划/资源身份、合法文件集合、提交身份、最终 writer 集合与结束标记、全部逻辑输入分片完成证明 | T03 确认的真实提交与运行终结信息 |
| Manifest | 固定 manifestId、证据摘要、排序后的显式文件列表、Schema、SHA-256/字节/行数、固定源版本 | 完整提交证据及实际文件回读 |
| TerminalObservation | CR UID、generation、Flink Job ID、成功终态及持久观察记录 | 受控 Operator/Flink 查询；Pod Running 不是终态 |
| StageReceipt | 对已确认阶段事实的引用及确定结果 | 上述事实和元数据库记录，可重建，不作为循环自证 |

规范化摘要采用 UTF-8 JSON，键排序、文件列表按规范对象键排序；禁止浮点编码金额，时间采用固定 UTC 表示。不可变内容中的时间取原始计划/提交证据，恢复进程的当前时间单独记审计字段。每个规范版本固定算法，禁止同一标识在不同恢复轮次产生不同语义摘要。当前最小共同载荷、七类 kind 与规范版本 `magic-flink-canonical-v1` 见 [SQL 与摘要合同](../../p0/sql-and-digest-contracts.md)第 4、5 节；完整领域对象与跨引用来源核验尚待补齐。

### 5.2 首轮实验的收敛配置

- 显式 BATCH，不用 streaming checkpoint 完成回调替代批结束协议。
- 固定并行度，关闭推测执行及自动并行度变化；不启用 compaction、自动 schema 演进或动态分桶。解除这些限制需新增相应验收。
- 每次平台尝试使用独立前缀；批内多文件滚动可用，但不能依赖墙钟分桶决定 manifest 身份。
- 提交证据只有在 T03 定义的完整集合成立后才写最终索引；局部记录、预提交消息和半份索引都不能 SEALED。
- JobManager 失败后是否能保留进度，由选定版本和配置实测；无法证明旧产物完整时，确认旧执行终止后从原固定输入用新尝试重跑。不要求 P0 实现所有批作业断点恢复。
- 成功终态丢失且无法恢复时不以完整文件反推成功；保持 UNKNOWN，只有明确确认停止后才能废弃重跑。

FileSink 的批模式与流模式文件可见性不同，官方说明见 [FileSystem/FileSink](https://nightlies.apache.org/flink/flink-docs-release-1.20/docs/connectors/datastream/filesystem/)。这些说明支持选型研究，不能替代本项目 CommitEvidence 的实验。

### 5.3 必须证明的六个不变量

1. 每个进入 Manifest 的文件属于一个明确、合法、当前尝试的提交集合。
2. 完整性由预期集合与终结证据共同决定，不由“已收到多少条成功消息”猜测。
3. Manifest 已写但未被元数据库接纳时，下游不可见。
4. SEALED 引用与阶段完成同事务更新；同 ID 不允许不同内容。
5. 证据完整时只补建清单/回执，不重新执行数据图；证据不完整时不抢救拼接文件。
6. 旧尝试、取消后的证据可以归档，但不能影响当前尝试、下游意图或发布授权。

| 单阶段 / 单实验 | 15 分钟 / 30 分钟 | 超时停止新尝试，但继续追踪已发生副作用 |
| 自动阶段重试 | 最多 1 次 | 缺提交证据的废弃重跑和 INLINE 转 FLINK 都消耗预算 |
| 输入/证据保留 | 本次实验结束后至少 7 天 | 仍被活动实验引用时不回收；行内策略更长则从其规定 |

其他未来连接类型的请求限速在 P4 确定；P0 不用未经测量的 HTTP/BQ 预算冒充四源资源配置。首次准备数据和测试保留期不得涉及真实客户数据。
